사용자 입력: $ARGUMENTS

위 입력을 바탕으로 **새 프로젝트의 설계 문서 세트**를 만든다. 이 명령은 설계와 기획만 한다. 소스 코드, 프로젝트 폴더, 의존성 파일은 만들지 않는다. 산출물은 `docs/` 아래의 Markdown 파일뿐이다.

모든 응답과 문서는 한국어로 작성한다. 코드 식별자와 기술 용어는 원문을 유지한다.

## 0. 입력 확인

- 사용자 입력이 비어 있으면 작업을 시작하지 말고 "어떤 기능이나 프로젝트를 개발할지 한두 문장으로 알려 주세요. 예: /dev 할 일을 관리하고 마감일 알림을 보내는 웹 앱"이라고 안내하고 멈춘다.
- 입력이 있으면 프로젝트 이름을 정한다. 영문 kebab-case(예: `todo-reminder`)를 쓰고, 한글 이름이 더 자연스러우면 한글을 함께 적는다. 이름은 네가 정하고 응답에 명시한다.

## 1. 현황 파악

- `myAgent/` 안에 기존 프로젝트, `CLAUDE.md`, `docs/`가 있는지 `Glob`으로 확인한다. 같은 주제의 설계 문서가 이미 있으면 덮어쓰지 말고 `Read` 후 갱신한다.
- 상위 폴더 `AI_myClaude/`의 기존 프로젝트(`mySchedule`, `myExpense`, `myShopping`)를 보고 코드 스타일, 저장 방식, 실행 방식이 참고할 만한지 확인한다. 재사용 가능한 패턴이 있으면 설계에 반영한다.

## 2. 요구사항 분석

`requirements-planner` 에이전트의 방법론을 따른다. 에이전트를 호출할 수 있으면 `Agent` 도구로 위임해도 된다. 어느 쪽이든 결과는 같은 형식이어야 한다.

- **목표와 문제**: 해결하려는 문제와 성공의 정의
- **대상 사용자와 사용 상황**
- **기능 요구사항**: 사용자 스토리 형식, 각 항목에 완료 기준
- **비기능 요구사항**: 성능, 보안, 데이터 보존, 접근성, 호환성
- **범위**: 포함 항목과 제외 항목을 분명히 구분
- **제약 조건**: 플랫폼, 언어, 외부 서비스, 기존 프로젝트와의 관계
- **가정**: 입력에서 정해지지 않은 사항은 기본값으로 채우고 전부 가정으로 기록한다
- **미결정 사항**: 사용자가 결정해야 하는 것만 모은다. 최대 5개까지 번호를 매겨 응답 마지막에 묻는다.

## 3. 시스템 설계

- 아키텍처 개요: 주요 구성 요소와 역할, 구성 요소 간 데이터 흐름
- 기술 스택: 후보를 2~3개 비교하고 하나를 추천한다. 추천 이유와 트레이드오프를 적는다. 최종 선택은 사용자 몫이다.
- 데이터 모델: 주요 엔티티, 필드, 관계. 저장 방식(파일, SQLite 등)을 명시한다.
- 주요 인터페이스: 화면 또는 CLI 명령, API 엔드포인트 중 해당되는 것
- 예외 처리와 오류 메시지 방침

## 4. 폴더 구조 설계

- 프로젝트 루트 아래의 전체 트리를 코드 블록으로 작성한다.
- 각 폴더와 주요 파일에 한 줄 설명을 붙인다.
- 기존 `mySchedule/`의 구조(단일 `main.py` + 모듈)처럼 이 저장소의 관례를 따를 수 있으면 따른다. 관례와 다른 구조를 택하면 이유를 적는다.
- 테스트, 설정, 데이터 파일 위치를 포함한다.
- 실제 폴더는 만들지 않는다. 설계 문서에만 적는다.

## 5. 실행 계획

- 작업 분해(WBS): 각 작업에 ID, 제목, 선행 작업, 완료 기준을 붙인다.
- 우선순위: MoSCoW로 구분한다.
- 마일스톤: 동작하는 중간 산출물 단위로 묶는다 (M1: 최소 동작 버전, M2: 핵심 기능 완성 등).
- 리스크와 완화 방안

## 6. 산출물 저장

프로젝트 이름이 `<name>`이면 다음 파일을 `myAgent/docs/<name>/` 아래에 만든다. 폴더가 없으면 만든다.

- `requirements.md`: 요구사항 명세 (2번 결과)
- `design.md`: 시스템 설계와 기술 스택 비교 (3번 결과)
- `structure.md`: 폴더 구조 설계 (4번 결과)
- `plan.md`: 작업 목록, 마일스톤, 리스크 (5번 결과)

각 파일 상단에 작성일, 상태(초안), 원본 입력 문장을 적는다.

## 7. 최종 응답

응답에는 다음만 간결하게 담는다.

1. 프로젝트 이름과 생성된 파일 경로 목록
2. 핵심 설계 결정 3줄 이내 (기술 스택 추천, 폴더 구조의 핵심, 마일스톤 개요)
3. 사용자가 결정해야 할 미결정 사항 (번호 매김, 최대 5개)
4. 다음 단계 제안: 미결정 사항에 답하면 설계를 갱신하고, 구현은 명시적 요청이 있을 때 `implementer` 에이전트로 진행한다고 안내한다.

## 금지 사항
- 프로젝트 폴더, 소스 파일, 설정 파일(`package.json`, `requirements.txt` 등)을 만들지 않는다.
- 사용자가 요청하지 않은 기능을 필수 범위에 넣지 않는다. 제안은 "Could" 또는 "제안"으로 표시한다.
- 확인하지 않은 기술 사실을 단정하지 않는다.
- 설계 결과를 채팅으로만 전달하지 않는다. 항상 파일로 남긴다.
